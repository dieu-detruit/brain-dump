# Brain Dump Watch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 推奨は後者によるこのセッション内での実装。ユーザーの計画レビューと実行方法の選択後に着手する。

**Goal:** Watchを閉じていても継続確認通知に回答でき、既存Threadへ実行を切り替えられるネイティブアプリを、Macを所有せずにビルド・導入できるようにする。

**Architecture:** SwiftUIのWatch単独アプリが、端末専用認証を持つSupabase Edge APIを呼ぶ。既存Web版で端末を紐づけ、DBの実行セッションを共有する。Supabase CronとAPNsで通知し、Codemagicでビルドする。

**Tech Stack:** SwiftUI / URLSession / Keychain / UserNotifications、PostgreSQL / pgTAP / Supabase Cron・Edge Functions、Deno / TypeScript、既存React / Vitest、XcodeGen / Codemagic。

**Spec:** [承認済み設計書](../specs/2026-09-24-watch-app-design.md)

## Global Constraints

- 初版は一覧・現在の実行・継続回答・切り替えを提供する。
- 55分で送信・60分で終了という既定の時間は維持する。
- コード有効期間は5分。
- 対応下限はwatchOS 10を初期案とし、ユーザーのWatchのOSがこれを満たすことを実機導入前に確認する。
- オフラインでは最後に取得した一覧を「未更新」と表示し、変更を黙って予約・後送しない。
- WebのSupabase refresh tokenをWatchと共有しない。
- APNs秘密鍵・service role keyはEdge FunctionsのSecretsへ保存し、WatchやWebへ渡さない。
- 実機通知の確認が済むまでは「Watchで利用できることを検証済み」としない。

実装はローカルファイルと開発用検証まで自律的に進める。本番DB反映、外部サービス接続、署名アップロード、TestFlight配布は成果物と必要な設定を用意した後に扱う。秘密値は会話やログに表示しない。Codemagicの無料枠を超える課金を自動で有効化しない。

## Review Focus

1. 古い通知・二重タップ・タイムアウト後の再送で、別の実行を確認したり確認期限を延長しない（Task 2・5・6）。
2. 紐づけの応答を取り逃した端末が、登録不能にも他人の端末にもならない（Task 3）。
3. Thread削除や端末解除が通信中に起きても、取り消された権限や古い表示で操作しない（Task 2・3・6）。
4. APNs送信後にワーカーが落ちても無期限に再通知せず、期限内の回復ができる（Task 5）。
5. OSがアプリを停止・再起動しても、秘密値と通知の対象を復元でき、失敗を成功表示しない（Task 6）。

## 共通API契約

DBのbigint IDはJSONでは文字列とする。確認世代にはUUIDを使い、時刻を丸めて比較しない。

```ts
type ExpectedExecution = { session_id: string; confirmation_revision: string } | null;
type ActiveExecution = {
  session_id: string; confirmation_revision: string; thread_id: string;
  last_confirmed_at: string; deadline: string;
};
type Snapshot = {
  server_time: string;
  threads: { id: string; title: string; delegation: "ai" | "colleague" | null; priority: number }[];
  active: ActiveExecution | null;
};
type Mutation = {
  operation_id: string; action: "confirm" | "switch";
  expected: ExpectedExecution; target_thread_id?: string | null;
};
type MutationResult = { status: "applied" | "stale" | "expired"; snapshot: Snapshot };
type ApiError = { error: "unauthorized" | "invalid_request" | "rate_limited" | "unavailable" };
```

`operation_id`はUUID。同じID・同じ要求の再送には保存済みの結果を返す。同じIDで異なる要求は400。期限切れ・競合はHTTP 409とMutationResult、成功は200、無効な認証は401、入力不正は400、制限超過は429、サービス障害は503。

WatchのAPI: `POST /pairings`、`POST /pairings/status`、`GET /state`、`POST /execution`、`PUT /push-token`。
Web向け承認・一覧・解除はSupabaseユーザーJWTを検証する別経路 `POST /pairings/approve`、`GET /devices`、`DELETE /devices/:id`。
Watch端末トークンはこれらWeb向け経路に使用できない。

- [ ] Watchは32byte乱数のpairing secretとdevice tokenを別々に生成する。開始要求にpairing secretとdevice tokenのSHA-256ハッシュを渡す。サーバーはsecretのハッシュとtokenのハッシュのみ保存する。承認時にtoken hashを端末レコードへ移し、Watchは自分が保存済みのtokenを利用する。この方式では承認応答の喪失時も秘密tokenの再発行は不要。

```ts
type PairingStart = { pairing_secret: string; device_token_hash: string };
type PairingStatus =
  | { status: "pending"; expires_at: string }
  | { status: "approved"; device_id: string }
  | { status: "expired" };
// status request = { pairing_id: string, pairing_secret: string }
// approve request = { code: string }, user identity = validated Supabase JWT
```

- [ ] 8桁コードは暗号学的乱数・有効コードの一意制約・衝突時再生成。開始は信頼できる送信元キーごと10回/時、照会はpairingごと30回/分、承認はユーザーごと5回/5分。制限はDBで原子的に更新し、Edgeインスタンス再起動でリセットされない。無制限なクライアント指定IPを制限キーとして信用しない。
- [ ] device token hashからownerを確定し、RPC呼び出し時にも端末失効を再確認する。解除と変更操作は端末→brain_stateの順でロックし、認証検査後の解除との競合も扱う。APIの成功結果やログにsecretを含めない。
- [ ] 入力サイズ16KiB、タイトルはDBからのみ取得、APNs tokenは最大256byteの16進表現、environmentはsandbox/productionのみ。新規作成・編集経路は実装しない。
- [ ] Edgeの標準JWTチェックは端末用経路を扱えるよう関数単位で設定し、全経路の明示的認証をテストする。service role資格情報はサーバーだけで使用。レート制限以外の内部情報はエラーに含めない。
- [ ] 実行: `deno test supabase/functions/_shared/watch-auth.test.ts supabase/functions/watch-api/handler.test.ts` と `pnpm dlx supabase test db`。承認応答喪失後も同じdevice_idで復帰することを追加確認する。

- [ ] CredentialStoreの読み取りは`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`を使用し、バックグラウンド通知処理でも初回アンロック後に読み出せるようにする。取得不可なら成功扱いせず再試行案内にする。ログへトークンを出さない。
- [ ] PairingViewは8桁コードと残り時間を表示し、3秒間隔の照会は画面アクティブ時だけ行う。通信断・再起動後は保存済みpairing情報から再開する。承認を確認したら通知許可を要求し、APNs tokenを登録する。
- [ ] ExecutionViewは現在のThreadと継続ボタン、優先順の一覧を表示する。長い日本語タイトルは複数行表示し、空一覧・実行なし・未更新・読み込み中を表現する。タップ中は変更操作を無効化する。アクティブ時15秒間隔と画面復帰時に更新し、バックグラウンドでタイマーを止める。
- [ ] UserNotificationsのアクションを登録する。

```swift
let confirm = UNNotificationAction(identifier: "CONFIRM", title: "続けている", options: [])
let change = UNNotificationAction(identifier: "SWITCH", title: "切り替える", options: [.foreground])
let category = UNNotificationCategory(identifier: "EXECUTION_CHECK_IN",
    actions: [confirm, change], intentIdentifiers: [], options: [])
UNUserNotificationCenter.current().setNotificationCategories([category])
```

- [ ] 通知処理はpayloadのsession_id・confirmation_revision・operation_idをそのまま使う。通常画面の現在値に置き換えない。`CONFIRM`はバックグラウンドAPI呼び出し、`SWITCH`は最新一覧へ遷移する。
- [ ] completion handlerは成功・期限切れ・認証失敗・通信失敗の全経路で一度だけ呼ぶ。API timeoutは8秒に制限し、失敗時は可能ならアクションなしのローカル通知でアプリから再確認するよう案内する。
- [ ] process再起動を模した通知テスト、古い通知テスト、API結果待ち中のThread削除・端末失効テストを追加する。通知許可拒否でもアプリ内操作が可能なことを確認する。
- [ ] Task 1のCodemagicコマンドで全XCTestを実行する。通知配送そのものとシミュレーターでのハンドラーテストの結果を分けて報告する。

**Files:** Modify `codemagic.yaml`, `brain-dump-watch/README.md`, `brain-dump/README.md`; Create `brain-dump-watch/scripts/archive.sh`, `ExportOptions.plist`, `docs/watch-rollout.md`.
